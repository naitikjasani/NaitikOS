## 1. What this is, and what it is not

The event log is an **integration log**, not event sourcing. That distinction is
the single most important thing on this page, and getting it wrong would quietly
create a second system of record.

| | Event sourcing | What this is |
|---|---|---|
| Source of truth for entity state | the log | the **entity tables** |
| Rebuild state by | replaying events | you don't — the rows are the state |
| Rebuild projections by | replaying events | replaying events ✓ |
| Payload contains | everything needed to reconstruct | **references only** |

So an event says *a workout was completed* and points at
`workout_session/8f2c…`. It does not carry the sets. §9.3 warns about exactly
this: two copies of one fact "drift", and a payload that restates a number is a
second copy.

**The log *is* the system of record for three things** the entity tables cannot
express: causality (`causationId`), cross-domain ordering (`sequence`), and
intent (`correlationId` — which rows belong to one user action).

### The rule, in one line

> **Events reference, they do not restate.**

Enforced mechanically in three places:

1. `validateEventPayload` (core) rejects **unknown keys**, so an extra field
   cannot appear by accident. The error names ADR 0005.
2. `registry.test.ts` asserts structurally that no payload field is named like a
   measurement (`weightKg`, `doseMg`, `*Value`) or like content (`text`, `notes`).
3. Any new *numeric* payload field fails CI until someone adds it to
   `REVIEWED_NUMERIC_FIELDS` with a written reason for why it is a count.

That third one is deliberately annoying. The annoyance is the enforcement.

## 2. The envelope

Every event has exactly this shape; only `payload` varies by type.

```ts
type DomainEvent<T extends EventType> = {
  eventId:       EventId;        // client-generated UUIDv7 (§5.7)
  eventType:     T;
  occurredAt:    string;         // when it happened in the world
  capturedAt:    string;         // when the client recorded it
  createdAt:     string;         // when the server accepted it
  actorId:       string;
  source:        EventSource;    // user | device_import | derivation | …
  version:       number;         // payload schema version
  subject:       { type, id };   // the row this is about
  payload:       EventPayloadMap[T];
  correlationId: CorrelationId;  // the user action this belongs to
  causationId:   EventId | null; // the event that caused this one
  metadata:      EventMetadata;  // traceId, deviceId, zone, hlc
  sequence?:     EventSequence;  // server-assigned total order
};
```

### 2.1 The four timestamps

They collapse into one another most of the time. The cases where they diverge
are the cases that matter:

| Field | Meaning | Diverges when |
|---|---|---|
| `occurredAt` | when it happened | backdating a missed dose |
| `capturedAt` | when the user told the device | logging offline in a gym |
| `createdAt` | when the server accepted it | the outbox drains hours later |
| `sequence` | total order | **always** — it is not a time |

§9.5 makes the same argument for the clinical domain: "A lab drawn on 12 March,
reported on 19 March, entered on 24 March is three different dates, all of them
true, all of them sometimes the one that matters."

### 2.2 Why `sequence` is a bigserial and not the UUIDv7 timestamp

`sequence` is the ordering that §5.8's sync watermark reads and the timeline
paginates on. It must be **gapless and monotonic**, which only a single writer
can guarantee. §5.7 has clients generate ids offline, so a phone with a wrong
clock would order itself incorrectly against everything else.

Two identifiers, two jobs: the id is the permanent identity, assigned by whoever
created the row; the ordering is assigned by the server on acceptance.

**Consequence worth knowing:** an offline batch that drains on Tuesday gets
Tuesday's sequences, even though `occurredAt` says Saturday. Replay follows
`sequence`, because a derivation must never run before the event it derives
from.

## 3. The registry

`packages/core/src/events/registry.ts` declares every event type: its payload
type, its current version, and how it renders on the timeline.

A feature **emits into** this registry; it does not define event types locally.
The timeline and the job router both dispatch on it, and a type they have never
heard of cannot be routed.

     `registry.test.ts` will not catch it — the test asserts the registry's own
     internal consistency, not this file. Treat the code as authoritative. -->

| Category | Types |
|---|---|
| `clinical` | `Medication.Taken` · `.Skipped` · `.Delayed` · `Supplement.Taken` · `Appointment.Created` · `.Attended` · `Report.Imported` |
| `body` | `Workout.Started` · `.Completed` · `.SetLogged` · `Weight.Logged` · `BodyMeasurement.Recorded` · `Sleep.Recorded` · `SkinRoutine.Completed` · `SkinState.Logged` |
| `mind` | `Mood.Logged` · `Journal.Created` · `.Updated` · `AnxietyEpisode.Logged` · `Practice.Completed` |
| `media` | `ProgressPhoto.Uploaded` · `Media.Uploaded` · `Document.Uploaded` |
| `life` | `Goal.Completed` · `Task.Completed` |
| `system` | `Observation.Recorded` · `DailyClose.Completed` |

### 3.1 Naming

`Domain.ThingHappened`, **past tense**. Past tense because an event is a record
of something that already happened and cannot be refused — a handler that treats
`WeightLogged` as a *request* to log a weight has misunderstood the direction of
the system.

### 3.2 The three descriptor fields

- **`category`** groups the timeline (§3.2's domain filter).
- **`significance`** decides what a collapsed view shows. A Daily Close is
  `primary`; each individual set inside a workout is `detail`, because a session
  of forty sets would otherwise bury everything else that day.
- **`clinical`** is read by the Consultation Pack (§2.2) and the consent layer
  (§10.10). Clinical events must not cross an inference boundary without an
  explicit grant.

`Practice.Completed` is the one mind event that is **not** clinical: a meditation
session is not a psychiatric record, and marking it so would pull it behind the
consent boundary for no benefit.

## 4. The bus

```
publish(drafts)
  │
  ├─ 1. seal      → fill envelope, validate payload      ── whole batch, atomic
  ├─ 2. append    → assign sequence                      ── same txn as the domain write
  └─ 3. dispatch  → handlers, in registration order      ── AFTER the commit
```

### 4.1 It is not a queue

§5.2 permits **exactly one** scheduled entry point, so there is no second
scheduler and no worker pool. Dispatch is synchronous and in-process.

That is a real constraint, not a simplification. At n=1 with ~50 actions a day
there is no throughput problem to solve, and a queue is a second piece of
infrastructure to operate against C3's "must survive three-week gaps in
attention". Work that must be deferred becomes a `deferred_task` row, which the
single nightly runner drains — see [background-jobs.md](background-jobs.md).

### 4.2 Dispatch happens after the append commits

A handler that ran before the commit could act on an event that is then rolled
back — which for a job enqueue means work scheduled for a row that does not
exist.

### 4.3 A handler failure does not fail the publish

The domain write and the event are committed. A broken projection is recoverable
by replay; rejecting the user's workout because a timeline handler is failing is
not. §5.12: "Failure never loses user input."

Failures are retried three times in-process — there is no backoff, because there
is no queue to back off into — and then written to `event_dead_letter`, which
§5.16 alerts on.

### 4.4 Handlers contain no business logic

A handler translates and delegates: it reads the event, calls a domain service or
enqueues a job, and returns. Logic inside a handler is logic that only runs when
an event fires, which means it cannot be tested directly and cannot be reused by
a code path that did not emit.

### 4.5 Idempotency

`isIdempotent` defaults to **false**, which is the fail-safe direction: a handler
wrongly assumed idempotent double-writes on every replay. Non-idempotent handlers
are gated on `event_handled`, whose composite unique index is the actual
guarantee — two concurrent dispatches race on the insert and one loses.

Handler names are ledger keys. **Renaming one is a migration**: the renamed
handler will re-process the entire log.

## 5. Replay

```ts
await bus.replay({ afterSequence?, types?, handlerNames?, batchSize?, ignoreLedger? });
```

Replay **rebuilds projections. It does not reconstruct entity state** — ADR 0005
rule 3: the entity tables are the truth and were never derived from events.

Paged (500 by default) rather than loaded whole: twenty years is ~400k rows
(§9.7), which is fine in Postgres and not fine in one JS array.

`ignoreLedger: true` is required when rebuilding a projection from scratch. The
ledger correctly says the timeline handler already saw event 4,000 — true, and
irrelevant once the timeline table has been truncated.

### Rebuilding the timeline

```ts
await timeline.clear();
await bus.replay({ handlerNames: ['timeline.project'], ignoreLedger: true });
```

Safe because the projector is pure. The integration test asserts the rebuilt
entries are byte-identical to the originals, which is what makes this a routine
operation rather than a hopeful one.

## 6. Versioning

Events are append-only and **never rewritten**. An event written in 2027 at
version 1 is still a version 1 event in 2039 — so a handler in 2039 must be able
to read it, and the only way that stays true is if every version bump ships an
upcaster at the same time.

### Upcast on read

`upcast` runs on the way out of the store. The alternative — a migration that
rewrites old rows — is rejected for the reason §9.1 rejects mutable
observations: "If a weight from 2027 can be silently edited in 2031, then no
number in the system can be relied upon."

### Adding a version

1. Change the payload type in `registry.ts` and bump its `version`.
2. Add an upcaster to `UPCASTERS`, from the previous version to the new one.
3. Add a case to `migrate.test.ts` with a **realistic old payload**.

Step 3 is not optional. An upcaster with no test is a guess about data that
already exists and cannot be re-created.

`UPCASTERS` is empty today — every type is at v1 — so the chain logic is tested
through `upcastWith`, which takes an injected table. That parameterisation exists
precisely because the untested alternative would first execute during the very
version bump it protects, under time pressure.

### Failing closed

An event whose version is **higher** than this build understands is refused, not
guessed at. §5.8 anticipates it: "Over twenty years there will be a stale phone
in a drawer", and the same applies to a rolled-back server reading what a newer
deploy wrote.

An event whose *type* this build does not recognise is **skipped on read**, not
fatal — `unknownEventTypes()` reports them. A rolled-back deploy must degrade,
not die.

## 7. Storage

| Table | Rows are | Mutable? |
|---|---|---|
| `domain_event` | the log | **no** — trigger rejects every UPDATE and DELETE |
| `timeline_entry` | a projection | yes, and truncatable |
| `event_handled` | the idempotency ledger | rebuildable |
| `event_dead_letter` | handler failures | resolved in place |

`domain_event`'s immutability is stricter than `observation`'s, which permits its
supersession columns to change. An event has no legitimate mutation at all.

The log is the highest-value target in the schema: one unauthorised read is a
complete behavioural history. RLS is enabled and **forced** on it, with zero
policies (§5.4).

## 8. Emitting an event

From a domain service — the normal case, where the event and the row commit
together:

```ts
await db.transaction(async (tx) => {
  const row = await createWorkoutSession(tx, input);
  await bus.publish([{
    eventType: 'Workout.Completed',
    occurredAt: input.finishedAt,
    actorId: actor.subjectId,
    source: 'user',
    subject: { type: 'workout_session', id: row.id },
    payload: { setCount: row.setCount, exerciseCount: row.exerciseCount },
    metadata: { zone: input.zone, traceId },
  }]);
});
```

Over HTTP — for events with no domain row of their own, and for the outbox:

```
POST /api/events
{ "events": [ … ], "idempotencyKey": "…" }
```

`actorId`, `eventId`, `capturedAt`, `createdAt`, `sequence`, and `version` are
**never** accepted from the wire.

## 9. Gotchas

- **A batch shares one `correlationId`.** Allocated once per `publish` call, not
  per draft. A Daily Close emitting a dozen events with a dozen ids renders as a
  dozen unrelated timeline rows.
- **`metadata` is closed.** No free-form bag. §5.11's rule — "the schema cannot
  represent user content, which makes leakage impossible rather than prohibited"
  — applies here too.
- **`Journal.*` payloads carry `hasPrompt` and nothing else.** Not even a
  character count: a length is a weak signal and still a signal.
- **Timestamps read back as ISO 8601** because `instant()` is a `customType` with
  a `fromDriver` normaliser. A driver-level parser override does *not* work —
  drizzle overwrites the timestamp OIDs after the client is built.
